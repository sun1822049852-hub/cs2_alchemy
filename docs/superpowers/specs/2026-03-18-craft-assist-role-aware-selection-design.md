# 辅助选材主辅分侧逼近设计

## 背景

当前辅助选材逻辑以“整体均值逼近目标相对磨损”为核心，主流程位于 `node_sidecar/src/services/craftAssistService.js`。现有实现存在两个问题：

1. `material.role` 仅在数据归一化时保留，没有真正参与后端选材决策。
2. 逼近目标时偏向整体均值贪心修正，无法表达“主料优先高于目标、辅料优先低于目标”的业务规则。

本设计将辅助选材改为“主辅分侧 + 非对称收敛”，并明确前后端职责边界：前端只提供材料范围和配置，具体选材计算全部放在后端。

## 目标

1. `material.role` 在后端选材中成为真实约束。
2. 选材计算始终以相对磨损为唯一计算基准。
3. 当 `overall > target` 和 `overall < target` 时，采用不同的逼近策略。
4. 保留现有同稀有度、去重、冷却过滤、最终阈值校验等基础约束。
5. 前端不再维护一份独立的选材算法，避免前后端逻辑漂移。

## 非目标

1. 不修改前端材料配置 UI 的交互结构。
2. 不引入新的接口参数。
3. 不重做皮肤范围推导逻辑。
4. 不删除现有最小成本分配求解器，只降低其职责。

## 现有职责边界调整

### 前端负责

前端仅负责：

- 维护材料列表与角色配置
- 提供每个材料的 `role`、`count`、`wear_min`、`wear_max`
- 提供 `target_wear`、`wear_filter_mode`、`blocked_ids`、`include_cooling`、`wear_offset_pct`
- 展示后端返回的结果、均值和错误信息

前端允许继续保留的本地逻辑：

- 默认范围推导
- 材料编辑和校验
- 请求构造和结果渲染

前端不再负责本地推演“选哪 10 件”。`node_sidecar/ui/app.js` 中与服务端同构的选材算法应降级为 UI 辅助或删除，后端 `node_sidecar/src/services/craftAssistService.js` 成为唯一真源。

### 后端负责

后端统一负责：

- 候选物品过滤
- 相对磨损计算
- 同稀有度约束
- 物品去重
- 主料 / 辅料优先池构建
- `overall > target` / `overall < target` 两套分支收敛逻辑
- 最终“小于目标”和偏移阈值校验
- 明确失败原因输出

## 核心定义

### 相对磨损

全流程只使用相对磨损参与计算，公式保持不变：

`relative = (float_value - minfloat) / (maxfloat - minfloat)`

### 均值

`overall` 为当前已选 10 件材料的相对磨损均值。

### 差值

每轮收敛都使用同一条定义：

`diff = target - overall`

### 槽位目标

当前被调整的一侧，对每个已选槽位计算：

`slotTarget = currentValue + diff`

`slotTarget` 是当前槽位的期望替换目标，不是绝对硬边界。真正的硬约束由分支规则决定。

## 初始选材

### 候选池

后端仍沿用现有候选过滤基础逻辑：

- 主库存中可炼金物品
- 非隐藏
- 非组件箱内
- 是否包含冷却中物品仍由现有开关控制

每个材料在当前输入范围内得到一组 `available` 候选，并基于目标值切出角色优先视图：

- `preferredAbove`：相对磨损 `> target`
- `preferredBelow`：相对磨损 `< target`

### 角色优先选初始解

- `main`：优先从 `preferredAbove` 选
- `aux`：优先从 `preferredBelow` 选
- 若优先池不足，则允许从该材料的剩余 `available` 中补齐

这里的“优先”不是硬限制。材料范围约束依旧由 `wear_min` / `wear_max` 决定。

### 同角色特例

如果 10 件全部属于同一角色：

- 全是主料
- 或全是辅料

则不再区分“先调这一侧再调另一侧”，当前 10 件直接作为唯一可调集合，按 `overall > target` 或 `overall < target` 的对应分支处理。

## 收敛规则

### 分支一：`overall > target`

该分支表示当前结果偏高，需要向下压低整体相对磨损。

#### 顺序

1. 先榨辅料
2. 辅料榨干仍无法通过，再榨主料

#### 当前侧替换目标

当前侧每个槽位使用：

`slotTarget = currentValue + diff`

因为此时 `diff < 0`，该目标会低于当前槽位值。

#### 当前侧方案选择

当前侧批量方案按如下优先级评分：

1. 如果存在能通过最终校验的方案，优先选最终结果最接近目标的方案
2. 如果当前侧还不存在通过方案，则选能让整体继续下降最多的方案
3. 在整体效果相同的前提下，再比较各槽位与各自 `slotTarget` 的接近程度

#### 换边条件

- 当前侧还能继续让整体下降，就继续榨当前侧
- 当前侧已经无法再改善，再切到另一侧
- 一旦得到满足最终校验的结果，可以直接收口

### 分支二：`overall < target`

该分支表示当前结果偏低，需要在不越界的前提下抬高整体相对磨损。

#### 顺序

1. 先榨主料
2. 主料榨干仍不足，再榨辅料

#### 当前侧替换目标

当前侧每个槽位仍使用：

`slotTarget = currentValue + diff`

因为此时 `diff > 0`，该目标会高于当前槽位值。

#### 硬约束

此分支全程必须满足：

`newOverall < target`

也就是说，收敛过程中不允许把整体抬到 `>= target`，不能让流程进入“大于目标”的情况。

#### 当前侧方案选择

在 `newOverall < target` 的前提下，按以下顺序选当前侧批量替换方案：

1. 优先选择能让整体更接近目标的方案
2. 在这些方案中，优先选择各槽位不超过 `slotTarget` 且最接近 `slotTarget` 的候选
3. 如果某个槽位不存在不超过 `slotTarget` 的可用候选，则允许使用超过 `slotTarget` 的候选，但仍必须满足替换后 `newOverall < target`

例如：

- `target = 15`
- 当前 `overall = 7`
- 某槽位当前值为 `2`
- 候选为 `6` 和 `9`

若 `slotTarget = 7`：

- 优先使用 `6`
- 只有在“不超过槽位目标”的候选不存在时，才允许考虑超过 `7` 的候选
- 即便候选超过 `slotTarget`，只要替换后整体仍 `< target`，仍然允许使用

#### 换边条件

- 当前侧还能继续提高整体且不越界，就继续榨当前侧
- 当前侧已经无法继续改善，再切到另一侧
- 两侧都无法继续改善时停止

## 批量替换而非单槽位贪心

单纯按某个槽位“最接近 `slotTarget`”进行替换会产生局部最优、整体错误的问题。

因此每轮调整必须基于“当前侧整体批量替换方案”评估，而不是逐个槽位立即落子。批量方案需要同时考虑：

1. 替换后整体均值是否更接近目标
2. 当前分支的硬约束是否满足
3. 当前侧是否已被榨到极限
4. 槽位与 `slotTarget` 的偏差

## 代码结构改造

### 保留的现有能力

保留以下基础函数或其职责：

- 相对磨损计算
- 候选库存过滤
- 按名称聚合候选
- 最终配方合法性检查

### 新增或改造的后端函数

建议在 `node_sidecar/src/services/craftAssistService.js` 中引入以下职责拆分：

- `buildRoleAwareInitialSelection`
  - 基于 `role` 和目标值构造初始选材结果
- `buildSideCandidatePools`
  - 为当前侧生成可替换候选池
- `buildSideReplacementPlan`
  - 生成当前侧的整批替换方案
- `scoreSideReplacementPlan`
  - 对当前侧方案进行分支感知评分
- `applySideReplacementPlan`
  - 将方案落到当前已选结果
- `iterateTowardTargetByRole`
  - 执行“榨当前侧到极限，再切另一侧”的主循环

### 现有函数的去留

以下现有修正函数不再作为主路径：

- `applyCraftAssistDeficitCorrection`
- `applyCraftAssistOverflowCorrection`
- `applyCraftAssistOffsetWindowCorrection`

它们可以被新收敛器替换，或保留为兼容辅助函数，但不再承担核心修正职责。

现有最小成本分配函数 `solveCraftAssistMinCostAssignmentForRarity` 保留，但降级为：

- 兜底失败提示器
- 下界估计器
- 调试辅助工具

不再作为主路径求解器。

## 最终校验

后端新收敛器得到结果后，仍然必须沿用现有最终校验规则：

1. 配方数量正确
2. 稀有度一致
3. 不重复
4. 结果均值满足现有目标要求
5. 结果通过现有偏移阈值校验

也就是说，新逻辑只替换“怎么选”，不替换“什么算合格”。

## 失败处理

需要为以下场景提供明确错误信息：

1. 优先池为空，但 fallback 也不足
2. 同稀有度约束无法满足
3. 当前侧和另一侧都已榨干，仍无法得到合格结果
4. 同角色特例下已经无可替换方案
5. 迭代状态重复或达到上限，疑似进入无效搜索

错误文案应尽量说明：

- 哪个材料或哪一侧先耗尽
- 当前最低 / 最高可达结果
- 是否已经进入 fallback

## 测试要求

当前仓库没有辅助选材相关测试，本次改造必须补充后端测试，至少覆盖：

1. `overall > target` 时先榨辅料，再榨主料
2. `overall > target` 时辅料侧中途已满足条件，直接通过
3. `overall < target` 时先榨主料，再榨辅料
4. `overall < target` 时全过程不允许整体越界到 `>= target`
5. 槽位优先选不超过 `slotTarget` 的候选
6. 当不存在不超过 `slotTarget` 的候选时，允许使用超过 `slotTarget`、但仍不越界的候选
7. 10 件全主料特例
8. 10 件全辅料特例
9. 两侧都榨干仍失败的场景
10. 与最终偏移阈值校验的衔接

## 风险

1. 当前前端和后端存在双份近似算法，实现时若不清理前端主算法，后续极易漂移。
2. 批量替换方案若实现为全排列搜索，复杂度可能过高，需设计受控的候选剪枝。
3. 若分支规则和最终校验衔接不清，容易出现“中间过程合理但最终仍被老规则打回”的困惑。

## 实施建议

建议先做三件事：

1. 在后端加测试，先把目标行为钉死
2. 在后端实现新的角色感知收敛器
3. 清理前端中不再作为真源的本地选材逻辑，仅保留 UI 和请求职责
