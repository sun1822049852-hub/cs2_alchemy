# 炼金使用组件物品设计

## 背景

当前炼金页的候选物品、配方校对与执行链都只围绕主库存展开：

1. 左侧可炼金候选池只包含主库存物品
2. 配方预览中的 `item_ids` 只会在连接后按主库存做存在性校对
3. 点击执行时，前端直接把每组 10 件物品提交到 `/api/craft/tradeup`
4. 虽然系统已经具备组件取出能力，但该能力只用于组件页中的单次取出/存入，不会参与炼金执行编排

魔尊现在需要补上一条新链：

1. 在炼金设置中增加“使用组件中物品”
2. 打开后，所有组件中的可炼金物品也能进入炼金候选池，并允许直接点入配方槽位
3. 组件物品的选择必须受主库存可用槽位严格约束
4. 执行时要先按组件串行取出本轮真正需要的组件物品，再执行炼金
5. 某个配方只要有任意组件物品未成功取出，该配方整组跳过，不允许带着残缺材料进入炼金提交
6. 取出失败的物品原地保留在组件中，不做自动候补、不做自动回滚、不自动重算新配方

## 目标

1. 在不改变旧炼金链行为的前提下，为炼金页增加“使用组件中物品”能力
2. 允许主库存物品与组件物品共同参与候选、选材、排配方
3. 在选择阶段就严格限制最多可选多少组件物品，避免执行时超出主库存空间
4. 保留未连接时基于旧快照继续预选的能力
5. 连接并刷新后，按“全库存（主库存 + 组件库存）”重新校对当前配方
6. 执行时按组件串行全量取出，再只提交已就绪配方到炼金接口
7. 对预取失败的配方进行明确保留与标红，便于用户手动处理候补材料

## 非目标

1. 不实现“部分失败后自动重算候补配方”
2. 不实现“执行过程中动态腾空位后继续滚动补货”
3. 不改变现有 `/api/craft/tradeup` 的旧调用语义
4. 不自动把预取成功但后续未被使用的物品重新存回组件
5. 不在本版重构整个炼金队列或组件任务队列架构

## 已确认产品规则

### 1. 使用组件中物品开关

在炼金设置中新增布尔开关 `使用组件中物品`：

1. 默认关闭
2. 与炼金页、组件页的共享炼金设置同步显示
3. 持久化到本地 UI 偏好中
4. 关闭时，行为保持当前版本不变
5. 打开时，候选池切换为“主库存 + 全部组件中的可炼金物品”

### 2. 离线预选与连接后校对

1. 未连接时，允许用户基于最近一次快照继续预选配方
2. 此时 pending 配方视为“未校验”
3. 一旦连接并刷新库存，前端立刻按全库存重新校对所有 pending 配方
4. 校对时：
   - 仍存在于主库存或组件库存中的 `item_id` 保留
   - 已不存在的 `item_id` 从对应配方移除
   - 仍存在但 `casket_id` 已变化的物品只更新来源快照，不判失败
5. 若某组配方校对后不足 10 件，则保留该配方，但视为待补齐，不自动删除整组

### 3. 组件物品选择规则

1. 组件中的普通皮肤条目允许直接点入当前配方槽位
2. `Storage Unit` 本体永远不进入候选池
3. 组件物品进入槽位后，必须保留其来源信息：
   - `source_scope = "component"`
   - `source_component_id`
   - `source_component_name`
4. 主库存物品进入槽位后，来源信息为：
   - `source_scope = "main"`
   - `source_component_id = ""`
5. 执行前不要求这些来源快照绝对可信；真正执行时以后端最新库存为准再次解析

### 4. 严格预裁剪

组件物品的选择上限采用“严格预裁剪”规则：

1. `组件已选数 X` = 当前所有 pending 配方 + 当前槽位中，来源为组件的已选物品总数
2. `可用数 Y` = 当前主库存可用槽位数
3. 只要 `X < Y`，就允许继续选择新的组件物品
4. 一旦 `X >= Y`：
   - 未被选中的组件物品从左侧候选列表隐藏
   - 已经选中的组件物品继续保留显示，便于移除或复核
   - 主库存物品继续正常显示、正常可选
5. 如果用户尝试继续点选一个未被选中的组件物品，前端直接拦截并提示空间不足
6. 如果用户移除了已选中的组件物品，使 `X` 回落，则被隐藏的组件候选重新出现

### 5. 执行失败规则

1. 执行阶段先处理组件取料，再处理炼金提交
2. 某个组件物品若取出失败：
   - 原地保留在原组件中
   - 该物品所属配方整组标记为 `prepare_failed`
   - 该配方不参与炼金提交
3. 其他完全就绪的配方继续执行
4. 系统不自动补位、不自动候补、不自动改配方
5. 失败配方在 UI 中保留并标红，文案为：`组件取出失败，已跳过`

## 方案对比

### 方案 A：前端扩候选 + 后端统一执行编排

由前端负责：

1. 设置开关
2. 全库存候选池
3. 严格预裁剪
4. 连接后全库存校对
5. 队列状态展示

由后端负责：

1. 执行前的容量再校验
2. 按组件串行预取
3. 按配方判定 ready / failed
4. 仅提交 ready 配方到炼金接口

优点：

1. 与现有组件系统、炼金系统边界清晰
2. 旧 `/api/craft/tradeup` 可保持零漂移
3. 新功能通过专用编排入口实现，便于验证与回退

缺点：

1. 前后端都要改
2. 队列条目需要补充更多来源/状态信息

### 方案 B：前端自己串起预取 + 旧炼金接口

优点是后端改动少，但缺点明显：

1. 前端状态机会过重
2. 组件取出进度、失败恢复、刷新中断都更难处理
3. 会把业务编排逻辑散落在 UI 中

### 结论

采用方案 A。

## 总体设计

### 1. 前端数据模型扩展

当前配方条目只保存 `item_ids`，本设计在不改变其主键语义的前提下，补充“来源快照”和“准备状态”：

```json
{
  "id": "recipe_xxx",
  "status": "pending|done|prepare_failed",
  "item_ids": ["asset1", "asset2"],
  "item_sources": {
    "asset1": {
      "source_scope": "main|component",
      "source_component_id": "123",
      "source_component_name": "蓝箱"
    }
  },
  "prepare_status": "pending|ready|failed",
  "prepare_message": ""
}
```

约束如下：

1. `item_ids` 仍是配方物品集合的唯一主事实
2. `item_sources` 只作为 UI 展示和执行规划辅助
3. `prepare_status` 与 `prepare_message` 只在执行后更新，不参与正常选材
4. `done` 仍表示已成功炼金产出；`prepare_failed` 表示执行前预取失败而跳过

### 2. 前端候选池扩展

当前 `getCraftCandidates()` 只读取主库存可炼金物品；新设计拆成两层：

1. `getMainInventoryCraftableRows()` 保持原职责不变
2. 新增 `getAllInventoryCraftableRows({includeComponentItems})`

其规则：

1. 组件本体不算候选
2. 打开“使用组件中物品”时，把带 `casket_id` 的可炼金物品纳入候选
3. 关闭时只返回主库存结果
4. 冷却开关继续在候选池上层统一过滤

### 3. 左侧列表展示

打开“使用组件中物品”后：

1. 左侧标题改为 `全库存可炼金物品（组件已选 X / 可用 Y）`
2. 组件来源条目在卡片/表格中额外显示 `组件: xxx`
3. 达到严格预裁剪上限后，候选列表自动隐藏未选中的组件物品
4. 已选中的组件物品即使达到上限，也要继续显示，避免用户看不到自己已经选了什么

### 4. 连接后全库存校对

新增统一的 `reconcileCraftQueueWithAvailableInventory()`，替代当前只按主库存校对的逻辑。

规则：

1. 校对集合 = 主库存可炼金物品 + 已加载的组件可炼金物品
2. 若某个 `item_id` 不再存在，则从对应配方移除，并累计“移除了多少失效物品”
3. 若物品仍存在但来源变化，则更新 `item_sources`
4. 校对完成后：
   - 配方不足 10 件则继续保留，等待用户补齐
   - 已完成配方不参与校对

### 5. 执行入口

新增专用接口，例如：

`POST /api/craft/tradeup-with-components`

请求体：

```json
{
  "username": "account",
  "allow_cooling": false,
  "use_component_items": true,
  "recipes": [
    {
      "queue_index": 0,
      "item_ids": ["a1", "a2"],
      "item_sources": {
        "a1": {
          "source_scope": "component",
          "source_component_id": "123",
          "source_component_name": "蓝箱"
        }
      }
    }
  ]
}
```

保持旧接口不变的原因：

1. 旧链稳定，避免结果漂移
2. 新链包含组件编排、预取状态、部分配方跳过等新语义，不应塞进旧接口

## 后端执行编排

### 1. 执行前空间硬校验

后端收到请求后，先重新读取最新库存快照或在线库存状态，计算：

1. 当前主库存可用槽位
2. 本轮所有 pending 配方中“仍需从组件取出”的唯一物品总数

若 `组件待取总数 > 主库存可用槽位`：

1. 整轮直接拒绝
2. 不启动任何组件取出
3. 不提交任何炼金请求
4. 返回明确提示，让用户先释放主库存空间

该拦截是前端严格预裁剪的后端兜底，防止用户预选后库存又发生变化。

### 2. 组件预取阶段

后端把所有 pending 配方中的组件来源物品按 `component_id` 分组，得到：

```text
组件A -> [item1, item2, item3]
组件B -> [item4, item5]
```

执行规则：

1. 组件之间严格串行
2. 每个组件只执行一次全量 `withdraw`
3. 预取结果记录到 `prepareResults[item_id]`
4. 失败的 `item_id` 不重试为其他方案，不自动回滚，不自动替换

### 3. 配方就绪判定

每个配方单独检查其 10 件物品：

1. 主库存物品天然算 ready
2. 组件物品只有在 `prepareResults[item_id] = success` 时才算 ready
3. 只要有任意 1 件不存在或预取失败，该配方整组判定为 `prepare_failed`

输出结果：

```json
{
  "queue_index": 2,
  "prepare_status": "failed",
  "prepare_message": "组件取出失败，已跳过"
}
```

### 4. 炼金提交阶段

1. 只收集 `prepare_status = ready` 的配方
2. 这些 ready 配方再交给现有 `craftService.runTradeUpBatch(...)`
3. `prepare_failed` 配方完全不进入炼金提交体
4. 若 ready 配方数为 0，则结束执行并返回“无可执行配方”

### 5. 结果返回

接口返回需要同时包含两层结果：

1. 预取结果
2. 实际炼金结果

前端据此更新配方队列：

1. `prepare_failed` 配方保留并标红
2. `done` 配方按现有方式展示产物
3. 未执行的待补齐配方继续保留

## 前端状态与交互

### 1. 选材阶段

1. 打开“使用组件中物品”后，组件物品可以像主库存物品一样点入当前槽位
2. 点击组件物品时，除了追加 `item_id`，还要同步写入 `item_sources`
3. 若达到组件上限，再点未选中的组件物品则直接提示空间不足
4. 移除槽位中的组件物品时，要同时回收 `item_sources` 和组件计数预算

### 2. 队列显示

右侧配方队列新增来源/准备摘要：

1. 普通 pending 配方：`组件取料：N件待准备`
2. 预取失败配方：红色状态行 `组件取出失败，已跳过`
3. 全库存校对后若移除了失效物品：`已校对：移除X件失效物品`

### 3. 执行按钮行为

点击执行时：

1. 若未启用“使用组件中物品”，仍走现有执行链
2. 若启用且本轮配方里没有组件物品，可直接走旧链或走新链的无组件分支
3. 若启用且存在组件物品，则走新接口

## 错误处理

### 1. 选择阶段

1. 组件物品达到上限：前端直接拦截并提示
2. 候选物品不存在于当前快照：连接校对时剔除并提示

### 2. 执行阶段

1. 后端空间再校验失败：整轮拒绝
2. 组件取出部分失败：失败物品原地保留，失败配方跳过，其他 ready 配方继续
3. 所有配方都 prepare_failed：不调用炼金接口，只返回准备失败结果
4. 炼金阶段失败：沿用现有 `tradeup` 错误处理，不自动把已取出物品送回组件

## 测试策略

### 1. 前端单测

至少覆盖：

1. 打开开关后组件物品进入候选且允许点选
2. 组件已选数达到上限后，未选组件物品隐藏，主库存物品仍可见
3. 未连接可预选，连接后按全库存校对
4. 校对时失效 `item_id` 会从配方中移除，但整组保留

### 2. 后端服务测试

至少覆盖：

1. 执行前空间不足时整轮拦截，不启动组件取出
2. 多组件场景下按组件串行预取
3. 某配方有 1 件组件物品预取失败时，该配方整组 `prepare_failed`
4. 同一批次中部分配方 ready、部分 failed 时，只提交 ready 配方到 `craftService`
5. 取出失败的物品仍保留在原组件

### 3. 集成测试

至少覆盖：

1. 组件物品 + 主库存物品混合配方
2. 离线预选后刷新连接，触发全库存校对
3. 执行完成后队列中同时出现 `done` 与 `prepare_failed` 配方

## 风险与控制

### 风险

1. 现有配方条目结构较轻，新增 `item_sources` 与准备状态后，渲染与同步点会变多
2. 组件任务队列与炼金执行链耦合后，若边界不清，容易出现状态漂移
3. 全库存校对若仍误沿用主库存逻辑，会把组件物品错误剔除

### 控制

1. 保持 `item_ids` 为唯一主事实，新增字段只做辅助
2. 新增独立执行接口，不污染旧 `/api/craft/tradeup`
3. 前端、后端都各做一层容量校验，保证严格预裁剪不被绕过
4. 为“部分成功、部分失败”场景补专门测试，锁定“失败配方不提交”的硬规则

## 实施顺序建议

1. 先补前端数据模型与候选池、严格预裁剪、全库存校对
2. 再补后端新执行接口与组件预取编排
3. 最后补队列状态显示与端到端测试
