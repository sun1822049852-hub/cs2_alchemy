# Steam 登录阶段进度条复用设计稿

日期：2026-04-12  
状态：已确认，待用户审阅  
范围：Steam 账号添加/重登弹层、登录阶段进度反馈、登录后库存刷新解耦  
关系：本设计补充 [2026-04-12-steam-relogin-key-first-design.md](./2026-04-12-steam-relogin-key-first-design.md) 中与“重登 UI 反馈”相关的部分；`key-first` 认证原则、`loginKey` 失效语义与重登约束仍沿用旧文档。

## 1. 背景

当前 Steam 账号的“添加账号 / 重登”已经统一收束到同一条底层登录链路：

- 前端弹出同一个 `accountLoginModal`
- 前端提交同一个 `/api/accounts/login-save`
- 成功后同步账号状态，并继续刷新当前账号

但用户在点击 `登录并保存` 或 `重新登录` 后，界面缺少明确反馈：

- 如果后端响应较慢，用户会误以为程序没有反应
- 现在“连接账号”的等待使用的是炼金/汰换已有的 overlay，而“登录账号”没有同等级反馈
- 登录成功后还会继续等待库存刷新，进一步放大“卡住了”的感知

本轮目标不是实现真实登录百分比，而是给登录动作补一个与现有风格一致的阶段式进度反馈，并把“登录成功”和“库存刷新完成”从感知上拆开。

## 2. 目标

- 让 Steam `添加账号 / 重登` 在真正提交登录后立即出现进度条
- 复用现有炼金/连接 overlay 的视觉与状态机，不新增一套登录专属弹层
- 登录进度只覆盖“登录并保存”本体，不再包含库存拉取等待
- `添加账号` 与 `重登` 继续共走同一套底层登录流程和同一套进度反馈
- 失败时保留原登录弹层语义，不让 overlay 吞掉错误信息

## 3. 非目标

- 本轮不实现后端实时登录进度推送
- 本轮不修改 `/api/accounts/login-save` 的接口契约
- 本轮不改变 `key-first` 的认证策略
- 本轮不把客户端会员登录或其他非 Steam 登录入口并入这套 overlay
- 本轮不重做 overlay 视觉

## 4. 方案选择

### 4.1 方案A：仅在 `loginAndSave()` 内硬编码 overlay

优点：

- 改动最直接
- 接入速度快

缺点：

- 登录与连接两处各自维护 overlay 调用
- 后续若别的入口也要复用，重复逻辑会继续扩散

### 4.2 方案B：抽共用进度 helper，连接与登录共同复用（推荐）

做法：

- 把当前连接链路里专用的 overlay 调用抽成通用 helper
- `refreshWithConnectionOverlay(...)` 继续走该 helper
- `loginAndSave()` 也改为走该 helper，但传入登录阶段文案
- 本轮不引入新的 overlay `mode`；登录链路仍复用当前 `connecting` 渲染模式，只更换标题和明细文案

优点：

- 保持现有 overlay 外观与行为一致
- 登录与连接共享同一套进度壳，后续扩展成本更低
- 能把“登录阶段”和“库存刷新阶段”清晰拆开

缺点：

- 需要小幅整理 `app.js` 中现有连接进度逻辑

### 4.3 方案C：新增登录专属 overlay

优点：

- 登录文案和结构可完全独立定制

缺点：

- 视觉重复
- 状态机重复
- 与当前“复用现有风格”的目标不符

### 4.4 结论

选择方案B。  
后续实现统一基于“共用 helper + 登录阶段文案”的思路推进。

## 5. 用户体验

### 5.1 添加账号

- 用户主动打开“添加账号”
- 输入账号、密码、令牌
- 点击 `登录并保存`
- 当前端基础校验通过后，立即出现与现有连接风格一致的进度 overlay
- overlay 按阶段提示当前动作，例如：
  - `正在提交登录信息`
  - `正在保存账号`
  - `正在同步账号状态`
- 登录保存成功后，overlay 立即结束，弹层关闭
- 库存刷新作为后续动作继续执行，但不再让用户停留在“登录中”

### 5.2 重登

- 用户因 `loginKey` 缺失或失效进入“重新登录”弹层
- 账号继续保持锁定，不可编辑
- 用户提交后，出现同一套登录进度 overlay
- 若成功，overlay 结束并关闭弹层；后续刷新单独进行
- 若失败，overlay 收起，原弹层保留；账号锁定规则保持不变，本轮不新增失败提交后的自动焦点跳转

### 5.3 失败体验

- 账号、密码、令牌缺失时：不弹 overlay，直接在原表单显示校验错误
- 登录请求失败时：先收起 overlay，再在原登录弹层显示错误
- 这能保证 overlay 只表达“程序正在执行”，而错误仍由登录弹层承接

## 6. 前端设计

### 6.1 共用进度 helper

现有连接链路里已经有：

- `createConnectProgressReporter()`
- `refreshWithConnectionOverlay(...)`
- `setCraftExecutionOverlayState(...)`

本轮不重写 overlay，而是将“打开、更新、关闭 overlay”的壳层抽成更通用的 helper，例如：

- `runWithProgressOverlay(...)`
- 或 `createProgressOverlaySession(...)`

该 helper 负责：

- 打开 overlay
- 接收阶段更新
- 结束时统一关闭 overlay

连接链路与登录链路都只负责提供自己的阶段文案和执行逻辑。

实现约束：

- 本轮必须继续设置 `state.craftProgressEnabled = true`
- 本轮必须继续通过 `setCraftExecutionOverlayState({ mode: "connecting", ... })` 驱动进度条
- 不允许为了区分“登录中”而新增 `login` 等新 mode，除非同时改造 `renderCraftExecutionOverlay()` 对进度条显隐的判断

原因：

- 当前 overlay 的进度条显示、样式类名和动画都硬绑定在 `mode === "connecting"` 上
- 若只抽 helper 却擅自改 mode，现有进度条可能直接不显示

### 6.2 登录阶段映射

登录 overlay 不追求真实百分比，只追求“用户知道程序在做什么”。  
建议阶段固定推进，例如：

- `25`：`正在提交登录信息`
- `60`：`正在保存账号`
- `90`：`正在同步账号状态`
- `100`：成功收口

说明：

- 百分比只是视觉占位，不对外承诺真实耗时
- 文案是主信息，百分比只是辅助节奏

### 6.3 `loginAndSave()` 的链路重排

当前 `loginAndSave()` 成功后会执行：

1. `/api/accounts/login-save`
2. `loadAccounts(...)`
3. `switchAccountView(...)`
4. `doRefresh(...)`

本轮调整为：

1. 表单校验
2. 进入登录 overlay
3. `/api/accounts/login-save`
4. `loadAccounts(...)`
5. `switchAccountView(...)`
6. 结束登录 overlay，关闭弹层
7. 触发后续库存刷新，但不再阻塞登录流程收口

这意味着：

- “登录是否成功”的边界前移到账号保存与当前账号同步完成
- `doRefresh(...)` 不再属于登录 overlay 的同步等待部分

阶段推进必须绑定到明确时序点：

| 阶段 | 百分比 | 触发时机 |
| --- | --- | --- |
| `正在提交登录信息` | `25` | 前端表单校验通过后，且在第一次 `await api(\"/api/accounts/login-save\")` 之前 |
| `正在保存账号` | `60` | `/api/accounts/login-save` 成功返回后，且在 `await loadAccounts(...)` 之前 |
| `正在同步账号状态` | `90` | `loadAccounts(...)` 成功返回后，且在 `await switchAccountView(...)` 之前 |
| 成功收口 | `100` | `switchAccountView(...)` 成功返回后，关闭 overlay 与登录弹层之前 |

失败回退规则：

- 任一阶段抛错，立即关闭 overlay
- 不执行后续阶段推进
- 错误仍回到原登录弹层状态区

### 6.4 overlay 所有权与并发

本轮共享的 `craftExecutionOverlay` 采用单所有者策略，不做排队，也不做多任务合并。

规则：

- 同一时刻只能有一个会话拥有 overlay
- 登录提交前若 overlay 已被连接流程或炼金流程占用，则本次登录不启动，并直接在登录弹层提示“当前有任务进行中，请稍后再试”
- 登录 overlay 一旦开始，到成功或失败收口前，其他流程不得覆盖该 overlay
- 登录成功后的后台库存刷新不再申请这层 overlay，避免与登录收口发生抢占

实现边界必须写死：

- 当前不止 `refreshWithConnectionOverlay(...)` 会写这层 overlay，`applyCraftComponentProgressEvent(...)`、炼金执行流、暂停提示等路径也会直接调用 `setCraftExecutionOverlayState(...)`
- 当前 overlay 的可见性还依赖 `state.craftProgressEnabled` 等底层状态字段，且代码中存在绕过 setter 的直接写入
- 因此“单所有者”不能只停留在新 helper 这一层
- 实现时必须二选一：
  - 把现有 direct write / clear 调用与 `state.craftProgressEnabled` 等 overlay 状态位写入，统一迁移到同一套 owner-aware controller
  - 或让所有会影响 overlay 渲染的底层入口都具备 owner-aware 仲裁能力，至少包含 `setCraftExecutionOverlayState(...)`、`clearCraftExecutionOverlayState()` 以及 `state.craftProgressEnabled` 的写入点
- 只改登录/连接 helper，而不约束这些 direct write 点和底层状态位写入，不算满足本设计

说明：

- 当前 `craftExecutionOverlay` 与连接/炼金共用同一份 `state.craftProgress*`
- 若不定义所有权，登录 overlay 很容易被其他流程覆盖或提前清空

### 6.5 模式约束保持不变

本轮不改变之前已确认的登录模式规则：

- `添加账号`：账号可编辑
- `重登`：账号锁定不可编辑
- 自动打开的 `loginKey` 失效重登弹层：默认焦点落在 `guard`
- 提交失败后不新增新的自动焦点回落语义；若后续需要补这条，另开一轮设计

overlay 只是额外反馈层，不能改写这些表单语义。

### 6.6 登录阶段文案显示位置

当前 `connecting` 模式下，`.craft-execution-detail` 默认隐藏，真正稳定可见的是进度环、百分比和 `title`。

因此本轮登录阶段文案必须遵守以下约束：

- `正在提交登录信息`、`正在保存账号`、`正在同步账号状态` 这些阶段文本统一写入 overlay `title`
- `detail` 在登录模式下可以留空，或只作为未来扩展字段，但不能依赖它承载当前阶段提示
- 若实现者希望同时显示副文案，必须在同一轮显式修改 `connecting` 模式下的样式与渲染规则；否则不算本设计默认路径

这条约束同样用于测试：

- 测试断言登录阶段文案时，应以 overlay `title` 为准，而不是 `detail`

## 7. 后续库存刷新解耦

### 7.1 原则

登录成功后，库存刷新仍然可以继续做，但它不再定义“登录是否还在进行中”。

### 7.2 行为

- 登录 overlay 只覆盖登录保存与账号状态同步
- overlay 收起后，再触发库存刷新
- 若库存刷新较慢，用户看到的是页面层面的刷新状态，而不是登录弹层一直卡住

后台刷新触发时序：

1. 登录 overlay 达到 `100`
2. 关闭登录 overlay
3. 关闭登录弹层
4. 以后台任务方式触发一次库存刷新

这里的后台刷新不再回写“登录中”语义。

### 7.3 失败语义

- 登录已成功，但库存刷新失败时，不回滚本次登录结果
- 刷新失败沿用现有页面 summary / 状态区提示
- 不再把库存失败包装成“登录失败”

### 7.4 后台刷新再触发重登的处理

本轮必须显式禁止“刚登录成功，后台刷新又立刻再次弹出重登窗”的重复打断。

规则：

- 登录成功后的第一次后台刷新，若返回 `reloginRequired`、`login_key_missing` 或 `login_key_invalid`
- 只更新页面 summary / 账号认证状态
- 不在这一轮后台刷新里自动再次打开重登弹层
- 用户后续手动点击刷新时，再按正常 `key-first` 规则决定是否打开重登弹层

这样可以确保：

- “登录成功”与“首次库存刷新失败”仍然是两个阶段
- 不会出现刚关掉登录弹层又立刻被新的重登弹层打脸的体验

## 8. 错误处理

### 8.1 表单校验错误

以下错误不应打开 overlay：

- 账号为空
- 密码为空
- 令牌为空

这些错误继续直接显示在登录弹层中。

### 8.2 登录请求错误

执行中的错误处理顺序为：

1. 收起 overlay
2. 恢复提交按钮可用态
3. 在原登录弹层显示错误

这样可以确保：

- 用户先看到“程序已停止执行当前登录动作”
- 再看到具体失败原因

### 8.3 模式相关错误

- `添加账号` 失败：保留用户输入，便于继续修正
- `重登` 失败：账号锁定规则不变
- 本轮不新增第三种登录弹层模式；错误仍在现有 `添加账号 / 重登` 两种模式内消化

### 8.4 提交过程中的关闭/取消语义

由于当前 overlay 本身 `pointer-events: none`，不会阻断用户点击弹层内按钮，本轮必须补齐提交流程中的交互规则。

规则：

- 登录 overlay 激活后，`loginSaveBtn` 保持禁用
- `clearAccountBtn` 在登录进行中也必须禁用
- 若存在关闭弹层的其他入口，在登录进行中一律视为无效
- 本轮不实现“取消网络请求”或中断登录；所有关闭动作都只是被忽略，直到请求成功或失败收口

目标：

- 避免用户在请求进行中把弹层关掉，导致 overlay 仍在跑、但表单状态已被清空或隐藏

## 9. 真实运行态验证要求

至少验证以下场景：

- 添加账号时，在第一次 `await api(\"/api/accounts/login-save\")` 之前，overlay 已进入可见态
- 重登时，在第一次 `await api(\"/api/accounts/login-save\")` 之前，overlay 已进入可见态
- 表单缺项时不出现 overlay，只显示输入错误
- 登录成功后，overlay 会在库存刷新完成前先结束
- 登录失败后，overlay 收起，登录弹层仍在，且表单约束未被破坏
- 自动拉起重登弹层时，账号仍然锁定且默认焦点落在 `guard`
- 重登提交失败时，账号仍然锁定，本轮不要求额外自动焦点跳转
- 登录进行中点击取消/关闭不会中断请求，也不会提前关闭弹层
- 登录成功后的后台刷新若再次要求重登，不会在同一轮自动弹出第二个重登窗

## 10. 测试策略

### 10.1 前端逻辑测试

至少覆盖：

- 登录校验失败时不打开 overlay
- 登录提交成功时按阶段更新 overlay `title`
- 登录成功后在调用库存刷新前关闭登录 overlay
- 登录失败时 overlay 收起且错误回到原弹层
- `添加账号` 与 `重登` 继续共走同一套 `loginAndSave()` 逻辑
- 登录进行中点击取消/关闭不会改变当前请求收口顺序
- 登录成功后的后台刷新若返回 `reloginRequired`，不会在同一轮自动再次打开重登弹层

### 10.2 连接链路回归测试

由于本轮会抽共用 helper，需补回归测试确保：

- 现有 `refreshWithConnectionOverlay(...)` 行为不回退
- 原连接入口仍能正常显示连接阶段 overlay
- `ensureCraftConnectedForExecution()` 这条直接使用 progress reporter 的路径也不回退

### 10.3 真实 UI 验证

在真实桌面应用中至少手动验证：

- 添加账号成功
- 重登成功
- 添加账号缺少令牌
- 重登失败并保留弹层

## 11. 验收标准

满足以下条件即视为本设计达成：

- Steam `添加账号 / 重登` 提交后都会立即出现统一风格的进度条
- 进度条只表达当前登录阶段，不承诺实时真实百分比
- 当前阶段文案以 overlay `title` 呈现，不依赖被隐藏的 `detail`
- 登录成功后，进度条在库存刷新完成前先结束
- 登录失败后，错误仍由原登录弹层承接
- 登录进行中无法通过取消/关闭动作打断本次请求收口
- 登录成功后的第一次后台刷新即便失败，也不会立刻自动再次弹出重登窗
- `添加账号` 与 `重登` 继续共走同一套底层登录流程
- 现有连接 overlay 风格与行为不回退
