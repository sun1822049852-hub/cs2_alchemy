# 远程控制台与本地签名授权快照设计稿

日期：2026-04-04  
状态：已完成脑暴确认，待按执行计划实施  
说明：本稿用于取代当前“客户端内嵌 admin 登录门”的过渡方案，目标是把管理控制面与本地业务数据面彻底拆开。客户端继续承载全部业务数据与交互，控制台只负责用户、会员、设备与功能授权。

## 1. 背景

当前仓库已经落地了第一阶段的本地 `admin` 登录门：

- `node_sidecar/src/appAuthStore.js`
- `node_sidecar/src/uiServer.js`
- `node_sidecar/ui/app.js`

这套实现能挡住匿名访问，也预留了 `RBAC`、`membership`、`Steam 账号绑定` 结构，但它仍然把“控制台鉴权”放在用户客户端里。

这与当前目标冲突：

- 用户拿到的是客户端，不应接触控制台
- 控制台只存用户与授权，不存本地业务数据
- 业务数据、Steam 登录态、库存、炼金、模拟仍然全部在本地执行
- 管理员需要远程控制用户可用功能、会员方案和撤权时效

因此，本轮设计不再强化本地 `admin` 登录门，而是改为：

- 独立控制台签发授权
- 客户端本地验签执法
- 通过短时效快照和静默续签实现近实时收口

## 2. 产品目标

### 2.1 首要目标

- 用户客户端中不再暴露控制台页面与控制台 API
- 控制台只负责：
  - 管理员登录
  - 用户管理
  - 会员方案
  - 功能矩阵
  - 设备绑定
  - 授权签发
  - 审计日志
- 客户端继续本地保存并执行：
  - `csgo_skins.db`
  - Steam 账号与 token
  - 库存快照
  - 炼金与模拟逻辑
  - UI 状态
- 客户端每次启动都先尝试静默获取最新授权快照
- 授权快照硬过期时间为 `15 分钟`
- 客户端运行中持续静默续签，授权撤回最迟 `15 分钟` 生效

### 2.2 非目标

- 不把库存、Steam 凭据、炼金结果上传到控制台
- 不把控制台改造成业务执行节点
- 不在本轮追求“绝对不可破解”的本地防逆向
- 不重写 SteamDT 数据更新工具链
- 不在本轮引入复杂在线计费，只预留会员与功能矩阵

## 3. 已确认约束

### 3.1 双域分离是硬约束

系统分为两个独立运行域：

- `Client`：用户安装包，包含现有 `node_sidecar` 本地业务引擎和 Electron UI
- `Admin Console`：单独部署的控制台，只给管理员使用，不随客户端分发

用户永远不会直接访问控制台页面，也不会持有控制台数据库。

### 3.2 授权模型不是单一 token，而是双凭证

参考浏览器 `set-cookie` 的会话思路，但不直接照搬浏览器 session。客户端使用两层凭证：

- `Entitlement Snapshot`
  - 由控制台签名
  - 客户端本地验签
  - 用于真正放行功能
  - 硬过期时间：`15 分钟`
- `Refresh Credential`
  - 首次激活或登录后由控制台下发
  - 客户端本地保存
  - 仅用于静默续签，不直接放行功能
  - 可撤销、可轮换、可绑定设备

### 3.3 离线宽限的真实含义

本项目采用“离线宽限模式”，但宽限并不独立于快照时间窗，而是：

- 客户端最后一次成功获取的 `Entitlement Snapshot`
- 在 `exp` 到来前都可继续本地使用
- `15 分钟` 到期后若仍无法成功续签，立即进入失效态

也就是说，离线宽限的最大持续时间就是当前快照剩余寿命，不能无限离线。

## 4. 推荐方案

本轮定版采用：

`远程控制台 + 本地签名授权快照 + 设备绑定 + 15分钟短时效续签`

原因如下：

- 比纯本地 `RBAC` 更符合“控制权只在管理员手上”的目标
- 比“每次功能调用都远程鉴权”更符合“全量交互在客户端本地完成”的目标
- 通过 `15 分钟` 快照时效，能把撤权和会员变更的生效滞后压到可接受区间
- 通过设备绑定和刷新凭证轮换，能显著提高凭证共享和复制客户端的滥用成本

## 5. 系统组件设计

### 5.1 Admin Console

控制台是独立 Node 服务，建议新建顶层目录 `admin_console/`。它负责：

- 管理员登录会话
- `client_user` 的增删改查
- 会员方案与功能矩阵维护
- 用户授权解析与签名
- 设备绑定管理
- 刷新凭证发放、轮换、吊销
- 审计日志写入

控制台数据库只保存控制面信息，不保存客户端业务数据。

### 5.2 Client Runtime

客户端继续以 `node_sidecar` 为核心，新增授权子系统，负责：

- 激活或首次登录终端用户
- 保存最近一次 `Entitlement Snapshot`
- 保存 `Refresh Credential`
- 每次启动时优先静默续签
- 运行中定时静默续签
- 根据快照内的权限矩阵本地放行或收口功能

### 5.3 Shared Contract

为避免控制台和客户端的字段漂移，需要新增共享契约层，统一：

- 功能 code 列表
- 授权快照 JSON 结构
- 过期判断规则
- `policy_version` 语义
- 权限矩阵展开规则

该共享层建议放在仓库顶层 `shared/` 目录，由控制台和客户端共同引用。

## 6. 数据模型

### 6.1 控制台数据库

建议最小表集如下：

- `admin_user`
  - 控制台管理员账号
- `client_user`
  - 终端用户账号
- `membership_plan`
  - 会员方案
- `feature_bundle`
  - 功能矩阵模板
- `user_entitlement`
  - 用户当前有效方案与功能覆盖
- `device_binding`
  - 用户与设备绑定关系
- `refresh_session`
  - 刷新凭证 hash、设备、状态、最近续签时间
- `audit_log`
  - 管理动作、设备换绑、撤权、登录、激活日志

可选扩展：

- `activation_code`
  - 一次性激活码

### 6.2 客户端本地数据

客户端继续保留这些本地数据，不同步到控制台：

- `csgo_skins.db`
- `login_keys.json`
- `inventory_ui_state.json`
- 本地 Steam 账号与库存快照
- 最近一次 `Entitlement Snapshot`
- 最近一次有效 `Refresh Credential`

其中，只有授权相关的新缓存与快照属于本轮新增。

## 7. 授权快照结构

建议采用以下最小字段：

```json
{
  "sub": "user_123",
  "username": "member_a",
  "device_id": "machine_xxx",
  "membership_plan": "pro",
  "permissions": [
    "accounts.read",
    "inventory.read",
    "inventory.refresh",
    "craft.use"
  ],
  "feature_flags": {
    "simulation_enabled": false
  },
  "policy_version": 7,
  "jti": "license_20260404_xxx",
  "iat": "2026-04-04T14:00:00.000Z",
  "exp": "2026-04-04T14:15:00.000Z"
}
```

签名算法建议优先使用 Node 内建 `crypto` 可直接支持的非对称签名方案，首版推荐 `Ed25519`：

- 私钥仅存在控制台
- 公钥打包进客户端
- 客户端不持有任何签发能力

## 8. 核心流程

### 8.1 首次激活

首次激活流程如下：

1. 用户在客户端输入终端账号凭据
2. 客户端收集本地 `device_id`
3. 本地服务调用控制台 `/api/client/activate`
4. 控制台校验账号、会员状态、设备绑定策略
5. 控制台创建或更新 `refresh_session`
6. 控制台返回：
   - `refresh_credential`
   - `entitlement_snapshot`
7. 客户端本地保存并立即验签
8. 验签成功后解锁可用功能

### 8.2 客户端启动

每次启动都必须先尝试续签：

1. 客户端读取本地快照与刷新凭证
2. 立刻向控制台发起刷新请求
3. 若刷新成功：
   - 替换本地快照
   - 替换刷新凭证
   - 进入正常运行态
4. 若刷新失败：
   - 若旧快照仍在 `15 分钟` 内，则临时放行并后台继续重试
   - 若旧快照已过期，则进入锁定态

### 8.3 运行中静默续签

续签策略固定为短周期而非接近过期才刷新：

- 建议每 `5 分钟` 刷新一次
- 或在剩余寿命小于等于 `5 分钟` 时立刻刷新
- 每次成功刷新都轮换 `refresh_credential`

这样能把撤权、降级、封禁的收口时间稳定控制在 `15 分钟` 内。

### 8.4 失效与锁定

满足以下任一条件时，客户端进入锁定态：

- 本地快照验签失败
- 本地快照字段不完整
- 当前时间超过 `exp`
- 控制台返回 `user_disabled`、`device_revoked`、`refresh_revoked`

锁定态下：

- 不再放行受控业务 API
- 显示“授权已过期，请联网同步”界面
- 只保留重新登录、重新激活、重试同步入口

### 8.5 撤权与会员变更

管理员在控制台做如下动作时：

- 封禁用户
- 切换会员方案
- 改功能矩阵
- 解绑设备
- 吊销刷新凭证

客户端不需要收到推送。下次静默续签即可生效，理论最迟 `15 分钟` 收口。

## 9. 客户端功能收口策略

现有客户端的权限点已经存在，可直接映射到新快照权限：

- `accounts.read`
- `accounts.write`
- `inventory.read`
- `inventory.refresh`
- `craft.use`
- `simulation.use`

控制原则如下：

- 默认拒绝
- 只有快照中显式存在的权限才放行
- `uiServer.js` 路由层和前端 UI 层都要同步收口
- UI 隐藏不是安全边界，真正边界仍在本地 API gate

## 10. 安全边界与现实限制

### 10.1 能做到的事

- 用户接触不到控制台入口
- 没有控制台私钥就无法伪造合法授权快照
- 设备绑定和刷新凭证轮换可提高分享与复制成本
- 撤权、降级、封禁在 `15 分钟` 内自然收口

### 10.2 做不到的事

- 纯客户端环境下，无法对强对抗逆向者做绝对防破解
- 本地缓存、内存 patch、时间篡改、二进制修改只能提高成本，不能保证绝对不绕过

本设计的目标不是“绝对不可破解”，而是：

- 管理面不落地到用户端
- 合法用户体验可用
- 撤权时效可控
- 普通滥用成本显著提高

## 11. 与当前项目的兼容策略

当前本地 `admin` 登录门仅作为过渡产物，后续处理策略如下：

- `Client` 版不再保留 `/api/auth/bootstrap-admin`、`/api/auth/login`、`/api/auth/logout`
- 现有 `appAuthStore.js` 不再承担运行时客户端授权职责
- 其中已有的 `RBAC` / `membership` 表设计可迁移到控制台数据库
- 现有 `accounts`、`inventory`、`craft`、`simulation` 的本地执行链尽量保持不动，只在路由入口替换 gate

## 12. 交付阶段

### 12.1 第一阶段：共享契约与控制台骨架

- 建立 `shared/` 共享契约
- 建立 `admin_console/` 基础工程
- 完成控制台数据模型、管理员登录、用户与授权管理

### 12.2 第二阶段：客户端授权运行时

- 新增本地授权缓存、续签调度器、控制台客户端
- 新增激活页、授权失效页
- 启动链改为“先续签后放行”

### 12.3 第三阶段：功能收口与移除本地 admin 门

- 用快照权限替换当前本地 `admin` gate
- 从用户版客户端移除控制台入口与控制台鉴权 API
- 完成文档、迁移脚本、上线前验证

## 13. 验收标准

以下条件同时满足，视为设计目标达成：

- 用户客户端里看不到任何控制台入口
- 控制台数据库中只存在用户、授权、设备、审计数据
- 客户端启动时一定先尝试静默续签
- 客户端失去联网后，最多只在当前快照剩余寿命内继续运行
- 管理员撤权后，客户端最迟 `15 分钟` 收口
- 本地业务数据仍全部在客户端执行，不回传控制台
